## 1. Where the assumptions note is not what the code shows

Corrections, each shown in the tables below. They are findings, not recommendations.

1. `analysis_catalog.yaml` carries **no** `executes_at`, cost, prerequisite or produces field (the note says it carries `executes_at`, `native_process_ref`, `requires_input`). `executes_at` is on the Egeria-side step (`SurveyStep`, `RE/surveyors/survey_definition_reader.py:220`); `native_process_ref` is under `egeria_registration` (1 of 66 entries sets it); `requires_input` is on 4 entries. Cost, `produces` and `requires_context` live on the Python `StepInfo`.
2. **`trellis-context` has no resolver and no resolver registry** (it holds `spec.py` and `packer.py` only). Resolution is in RE `context_compile.py`. Sections bind to **analysis ids** today (point 4).
3. Annotation construction in RE is **per annotation type** (`RE/surveyors/annotation_props.py:105-125`, 10 types), not per analysis; each surveyor builds its own `Annotation` objects (119 constructions in 42 of 45 `sub_surveyors/` files).
4. An "envelope" word already exists in RE with a different meaning: `Envelope` in `RE/facts.py:165` is an answer wrapper (subject, facts, `answerable`); the absence vocabulary the note wants is `RE/surveyors/result_status.py` and `Fact.state`, which is derived at read time and not stored with the result rows.
5. The note's "E3 observation states" exist in `/next` JavaScript (`RE/web/static/next/observation-state.js`, states none/proposed/confirmed/overridden/disagrees), not in a Python table.
6. EA has no analysis engine, annotation engine or results store. Its "reports" are pyegeria report specs.
