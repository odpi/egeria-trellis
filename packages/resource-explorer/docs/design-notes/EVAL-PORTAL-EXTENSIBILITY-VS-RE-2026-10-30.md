## 1. What the Portal has (its extension points, as built)

| # | Extension point | Mechanism | Where documented |
|---|---|---|---|
| P1 | **Report specs** (`FormatSet`: target type, formats, columns, action) | pyegeria's report registry; the Portal registers its own at import (`report_specs_handler.register_report_specs`, e.g. "Analytic - Element Count by Type", "Analytic - Generic Metric Trend") and pyegeria loads a CONFIG tier from `PYEGERIA_REPORT_SPEC_MODULES` (`module:callable` list) on first use; `refresh_report_specs()` re-loads it | README "Spec modules loaded through PYEGERIA_REPORT_SPEC_MODULES"; Egeria Explorer's Report Specs browser |
| P2 | **Analytic functions** (plain Python callables named by dotted path in a spec's `analytic_function`) | pyegeria `analytic_registry` (`AnalyticFunctionSpec`: name, function, description, returns, generic, binding_note, params, action, + `kind`/`source`/`version` since 6.2.3); `/api/analytics` lists them; demo specs prove each is runnable | `analytics_registry_handler.py` docstring; Analytic Functions Browser |
| P3 | **Dashboards** (Dashboard Sheet = ordered Placements of Reports made from specs) | authored with Dr.Egeria commands (Create Dashboard Sheet, Create Report, Link Report to Dashboard Sheet, Add Text on Dashboard Sheet); the sheet is a local JSON record, Reports/specs are Egeria elements; `local-dashboards.html` renders through the generic executor | `LOCAL_DASHBOARDS_TUTORIAL.md` (the tutorial: concepts, where dr_egeria runs — "the #1 gotcha" —, three steps, analytic reports with overridable parameters, explanatory text); `DIGITAL_PRODUCT_SUBSCRIPTION_TUTORIAL.md` (a business scenario) |
| P4 | **Governance Metrics panel** | reads Egeria `GovernanceMetric` elements with Report lineage (`governance_metrics_handler.py`); generated by `gen_governance_metrics.py` | `governance-metrics.md` |
| P5 | **Overview KPIs** | `overview_specs._TILES` + `overview_handler.py`, computed in the Portal with `overview_metrics` helpers; the honest-KPI rules of #603 §2 live here as code | `OVERVIEW_REPORTING_MODEL.md`, `egeria-overview.md` |
| P6 | **A remote producer's tile** (RE) | `re_analytics.py`: an analytic function that is an HTTP client — signs the viewer's persona into RE (`POST /api/auth/portal`, trellis SSO JWT), asks RE for `trellis_analytics.portal.curation_coverage_tile`, returns RE's dict unchanged; every failure is a `not_established` tile with the reason and no counts at the top level; registered through P1's CONFIG tier | `local-dashboards.md` "Resource Explorer's Curation Coverage tile" |

The tutorial is good at what it covers: how a person composes a dashboard from specs that exist. It does not cover
how a developer adds a spec or a function (that is the README section and P1/P2 docstrings), nor what a new function
must promise about its numbers.

## 2. What is missing, measured against RE's model

| Gap | In the Portal today | In RE/trellis today |
|---|---|---|
| **G1 A contract for what a number means** | a spec has `description`, `returns`, `binding_note`; a function returns whatever it returns; the honest-KPI rules are code in `overview_metrics` and prose in #603 | `Declaration`: result kind from a fixed vocabulary, measures with unit + as_of + value field (+ basis/capped/categories per the 2026-10-30 brief), four declared absence sentences, confidence by form, scope, answers; refused at registration when incomplete |
| **G2 Absence vs zero at the framework level** | handled per function (the RE tile puts no counts at the top level so BAR cannot chart zeros; `count_elements` folds failure into 0 — #603 lesson 1, unverified as fixed in 6.2.16) | result states measured / not_measured / not_permitted / not_applicable / measured_nothing with declared sentences, read by every consumer; gate rule |
| **G3 Discovery** | two env-var lists of `module:callable` strings (`PYEGERIA_REPORT_SPEC_MODULES`, analytic modules), set as defaults in a handler; load order matters (the handler comments record a case where neither the demo specs nor the RE tile loaded until a refresh was added) | one Python entry-point group `trellis.analytics`; installing a package is the registration; the start-up line names what loaded and what was refused |
| **G4 Generic rendering from the declaration** | `local-dashboards.html` renders known output formats (DICT/JSON/SERIES/BAR…); a tile's meaning is in the spec's prose | Understanding renders by `result_kind` (graph drawn; measure said with units; table); chat compiles extents; publish table writes-as from the declared annotation |
| **G5 Provenance on the tile** | the RE tile carries state/as-of/version because `curation_coverage_tile` puts them in the dict; the Portal's tile template shows what it is given | every measure travels with unit, as-of, run, confidence form; "N of M" from basis (brief) |
| **G6 Who may name a callable** | `_resolve_analytic_function` imports any dotted path (pyegeria 6.2.16) | same executor underneath once dashboards D1 lands — the gap is shared |
| **G7 Two copies of the Portal** | `egeria-freshstart/PyegeriaWebHandler` has no `analytics_registry_handler.py` / `re_analytics.py`; quickstart does | n/a — a Portal packaging fact the coordination must not forget |
| **G8 Gate** | tests per handler; no "add a spec without editing the page" walk recorded since #603 proposed one | the extensibility gate (§7), walked 2026-10-28/30, PASS |

What the Portal has that RE lacks: P3's person-authored composition (RE's dashboards note deliberately reuses it),
P4's governed metrics with lineage, P6's cross-service identity hand-off (RE consumes it), and the tutorials.

## 3. What of RE's approach to integrate into the Portal, and what not

**Integrate (small, in pyegeria, so both consume one thing):**
1. **The declaration block on `AnalyticFunctionSpec`** (optional field `declaration`, the trellis `Declaration`
   model moved up, or a pyegeria copy that trellis's `_TrellisManifest` then stops redefining). Portal functions
   (count_elements, metric_trend, the Overview helpers) declare result kind, measures with unit/as_of, absence
   sentences and, where they count, basis/capped/categories. The Analytic Functions Browser and the demo specs
   show the declaration's words. This is #603's §4 contract in the form that already exists and is gated.
2. **State-aware execution in `exec_report_spec`**: when the declared absence applies (result state ≠ measured),
   return the sentence and no top-level counts — generalising what `curation_coverage_tile` and `re_analytics`
   do by hand — so no BAR/SERIES can ever draw zeros for "could not look".
3. **Registry-name-only resolution** in `_resolve_analytic_function` (G6), with the entry-point group as the
   registration path (G3): a spec names a registered function; packages register by installing. Keep the env var as
   a second tier for a transition.
All three are pyegeria changes → logged in PYEGERIA_ISSUES.md per the gaps rule and designed in a cross-repo note;
RE does not fix pyegeria directly.

**Do not move:** RE's Understanding/Chat/Curate consumers (they are RE screens); RE's step runner, step_runs and
registry; the Dashboard Sheet (stays the Portal's); the Governance Metrics panel (stays Egeria-backed; RE's facts
reach Egeria as annotations and DataQualityRules through the two publish channels, not through this panel).

## 4. How to keep the extensions coordinated

1. **One registry, one spec type, one declaration** — pyegeria's `analytic_registry` is the meeting point. Trellis
   already subclasses `AnalyticFunctionSpec`; the Portal already registers into the same registry. Rule: a field
   needed by two consumers lives in pyegeria's spec; a field needed by one lives in that consumer's subclass.
   The 2026-10-30 brief's three fields start in trellis and are candidates to move up once the Portal declares anything.
2. **One discovery path** — the entry-point group, with pyegeria owning the group name (`pyegeria.analytics` or the
   existing `trellis.analytics` renamed); the Portal's env-var lists become that group's second tier.
3. **One gate, walked in both places** — the extensibility gate's legs 0–8 (no code change in the host; start-up
   names the step; renders; answers; absence; publish; manifest change) get a Portal twin: "add a spec and a function
   by installing a package; the Analytic Functions Browser lists it with its declaration; a Dashboard Sheet can place
   it; a failing backend yields the declared sentence, never zeros." Written once, in trellis's note; walked by the
   architect on both apps.
4. **One tutorial pair** — keep `LOCAL_DASHBOARDS_TUTORIAL.md` as the composer's tutorial; add a developer's
   tutorial ("add an analytic function the honest way": declaration first, fixtures, registration by package) that
   RE's user-guide extension chapter and the Portal docs both link to, written once in trellis-analytics and copied
   by the docs sync, not maintained twice.
5. **Version coupling stated** — each app's image pins its pyegeria; a declaration field used by a spec must name
   the pyegeria version that reads it (`since`), the way `kind/source/version` arrived in 6.2.3.
6. **G7** — freshstart and quickstart PyegeriaWebHandler copies must carry the same analytics handlers, or the
   freshstart image has no analytics extension at all; one of them should import the other, not copy it.

## 6. Owner ruling (architect chat, 2026-10-30) and the plain version of this note

Owner's words: "I agree that we need to view core extensibility functions in pyegeria. It seems to me that we should
support a common library (maybe in git) of steps and analytic functions that can be enabled for plain report_specs,
in the portal, in re and probably ea."

**In one page, for anyone:**
- **pyegeria holds the core.** The registry of analytic functions, the model that says what a result means (its unit,
  its as-of, its "nothing" sentences), the executor that returns the sentence instead of zeros, and the rule that a
  report spec may only name a registered function. Every app gets these by using pyegeria.
- **One common library holds the functions and steps**, in its own git repository, released as a package anyone can
  install. Today that library is `trellis-analytics` inside the trellis monorepo; the ruling moves it to a home of its
  own. It depends on pyegeria and on nothing else. It never contains an application.
- **Four hosts enable what they need from it:** a plain report spec (anyone with pyegeria), the Portal (tiles and
  dashboards), Resource Explorer (surveys, questions, chat, publishing), and Egeria Advisor. A host chooses which
  functions are on; it does not copy them.
- **What this changes in the notes above:** §3's three pyegeria items stand, now as the definition of "core". §4.1's
  rule ("a field needed by two consumers lives in pyegeria") stands. §4.2 discovery: the library's entry-point group
  is named by pyegeria. The lifecycle note's decision 1 is answered: the reference steps leave the trellis workspace
  with the library, which also ends the "uv sync removed the steps" problem for good.
- **Open:** the repository's name and owner; whether EA's report specs need anything the Portal's do not; the first
  release's contents (the eight reference steps, curation_coverage, context_pack, the declaration model).
