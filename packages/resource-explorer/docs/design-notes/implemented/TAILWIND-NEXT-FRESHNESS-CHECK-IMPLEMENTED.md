# tailwind-next.css freshness check (implemented)

**Implements:** the design session's explicit dispatch to close
`docs/Backlog.md`'s "MEDIUM — `tailwind-next.css` has no build-freshness check and
will silently go stale again" entry with an actual, CI-enforceable fix rather than
another note.
**Branch:** `re/tailwind-css-freshness-check`, off `origin/main` at `100e131a`
("Merge pull request #339 from dwolfson/re/relationship-graph-rendering").
**Date:** 2026-09-28.

---

## 1 · The problem this closes

`resource_explorer/web/static/next/tailwind-next.css` is the ONLY stylesheet
`/next` loads — no CDN, no JIT, `index.html:292` links it directly as a committed,
pre-built artifact. It's generated by:

```bash
cd packages/resource-explorer/frontend-build
npx tailwindcss -c tailwind-next.config.js -i ./input.css \
  -o ../resource_explorer/web/static/next/tailwind-next.css --minify
```

Twice in two days an agent added new Tailwind class names to `next/*.js` or
`stages/*.js` and never re-ran that build. Both times the new classes rendered as
*literally nothing* — no error, no console warning, no visual cue beyond the
broken layout itself, because a class with no matching CSS rule is indistinguishable
from a class that was never applied. The second occurrence's own "live
verification" didn't catch it, because it tested function (did the dropdown work),
not appearance (did it look like a dropdown).

Two independent checks close this, both as pytest tests so they run in the same CI
job as everything else rather than as a separate process nobody remembers to run:

1. `tests/test_tailwind_next_freshness.py` — rebuild-and-diff.
2. `tests/test_tailwind_next_class_coverage.py` — grep-based literal coverage.

Neither replaces the other. (1) catches "the CSS hasn't been rebuilt since a JS
change" categorically, by re-deriving the whole file. (2) catches "this specific
class name will never compile even after a rebuild" — a typo, a color token that
doesn't exist in `tailwind-next.config.js`, a spacing step past the end of the
scale — which (1) also reports (a diff would show it too) but (2) names the exact
class and the file it's used in, which is a faster read on a long CI log.

## 2 · Check 1 — rebuild and diff (`test_tailwind_next_freshness.py`)

Runs the exact recorded build command against a `tmp_path` output file and
byte-for-byte diffs the result against the committed `tailwind-next.css`. On
mismatch it fails with the rebuild command and the first point of divergence (a
minified single-line file makes a full-text diff useless, so the message instead
shows ~150 characters of context around the first differing byte from both sides).

**Reproducibility, verified empirically (2026-09-28), not assumed:** ran the build
twice in a row from the same source tree — the two outputs were byte-for-byte
identical (`diff` reported no difference). No whitespace/formatting normalization
was added to the comparison, because there's nothing to normalize away; adding it
anyway would have made the check tolerate a real staleness case just as easily as
harmless build-order noise that doesn't actually occur here.

**Guard, not silent skip.** The test skips only when the *pinned* CLI isn't
installed — `shutil.which("npx") is None`, matching this repo's existing
`node`-availability convention (`test_next_enrichment_persistence.py` and others),
plus a check that `frontend-build/node_modules/.bin/tailwindcss` actually exists.
The second half matters: `npx` alone would silently auto-install *some* version of
`tailwindcss` from the registry on a cache miss, making the test's result depend on
network access and on whatever the registry resolves that day rather than on the
version pinned in `frontend-build/package-lock.json`. Skip reason names the exact
fix (`npm ci` in `frontend-build`).

## 3 · Check 2 — grep-based class coverage (`test_tailwind_next_class_coverage.py`)

Extracts every literal Tailwind class used inside a `class="..."` attribute across
`resource_explorer/web/static/next/**/*.js` (30 files: the top-level `next/*.js`,
plus `stages/*.js` and `admin/*.js`) and asserts each one exists in the compiled
`tailwind-next.css` (or, for the documented handful of non-Tailwind structural
classes, in `index.html`'s own inline `<style>` block — see §3.3).

### 3.1 · Mirroring Tailwind's own scanning, not inventing a parser

`tailwind-next.config.js` has no custom `content.extract` function, so Tailwind's
own default scanner is syntax-unaware: a broad regex over raw file text that finds
quote/backtick/`${`/`}`/whitespace-delimited candidate tokens. It does not parse
JS. That's *why* a class built as
`` `${isOpen ? 'border-accent bg-chrome-line/20' : 'border-chrome-line'}` `` compiles
correctly — Tailwind sees the two complete literal strings inside the ternary
branches and never has to understand "ternary" as a concept.

This check reuses that same "collect complete literal strings, ignore everything
else" rule rather than a heavier JS-aware approach, with one refinement that turned
out to be necessary: it is ternary-*shape*-aware (splits `${...}` content on
top-level, unquoted `?`/`:`, respecting quotes so a `hover:text-x` class inside a
literal doesn't get split on its own colon) so it can tell a **value position**
apart from a **condition position**. A first pass that grabbed every quoted string
inside `${...}` regardless of position produced real false positives: in

```js
class="... ${sort === 'size' ? 'text-ink' : 'text-accent-ink underline'}"
```

`'size'` is a comparison operand, not a class — a naive scanner (and a first
version of this one) flagged `size`, `confidence`, `worthy`, `undecided`, `Failed`,
`all` as "missing" this way, none of which were ever meant to be classes. The
ternary-aware split fixed all six by only accepting a fragment between `?`/`:`
separators that is *wholly* a single quoted literal — the same answer Tailwind's
own scanner reaches by a different (syntax-blind, not syntax-aware) route.

### 3.2 · Documented false-negative gap: fully dynamic interpolations

An interpolation with **no** literal branch at all — `${cls}`, `${mutedCls}`,
`${hoverCls[tone]}`, `${chip(state.scope === id)}` — is invisible to this check,
exactly as it's invisible to Tailwind's own build. Neither can resolve a bare
identifier or function call to a string without running the program. This is a
known, permanent limitation, not a bug to fix later — Tailwind's own documented
guidance is "never construct class names dynamically" for exactly this reason, and
where this codebase does it anyway (`chip()`, `mutedCls`, `hoverCls[...]`), the
resulting class names have to be covered some other way (typically: the same
literal also appears elsewhere in a non-dynamic `class=` attribute, or the function
itself is worth its own review — out of scope here).

75 such interpolations were counted across `next/**/*.js` on 2026-09-28. Rather
than silently accept whatever this number drifts to, `test_dynamic_exclusion_count_
has_not_jumped_unexplained` pins it (with a small slack) as a tripwire — not a
correctness check on any specific class, since none in this bucket can be named,
but a signal that a large jump in "surface this check can't see" is itself worth a
human look.

### 3.3 · Two small, reviewed allowlists — not silent exclusions

Two categories of finding don't belong in the "must exist in tailwind-next.css"
rule, and both live as explicit, commented dicts/sets at the top of the test file
(not as source comments in `next/*.js`, since this task's scope was tests + CI
config only — `next/*.js` belongs to other agents' branches tonight):

- **`KNOWN_HOOK_ONLY_CLASSES`** — classes used purely as DOM query-selector /
  event-delegation hooks, never meant to carry a CSS rule: `fb-star`
  (`feedback.js`, `.closest('.fb-star')`), `wl-band`, `wl-bar`, `wl-countrow`
  (`worklist.js`/`app.js`, row/marker classes), `inv-new-purpose`
  (`stages/investigation.js`, `querySelectorAll('.inv-new-purpose:checked')`).
  Confirmed absent from both `tailwind-next.css` and `index.html`'s `<style>`
  block for all five — this is a judgement call about intent, not a parsing gap,
  so it's reviewed here rather than hidden.
- **`KNOWN_PREEXISTING_GAPS`** — classes this check's first run found that were
  genuinely uncompiled and **not** dynamic-pattern false negatives: `gap-s5`,
  `mb-s5`, `mt-s5` (the spacing scale only defined `s1`/`s2`/`s3`/`s4`/`s6`/`s8` —
  no `s5`), and `bg-paper-raised`, `border-rule-soft`, `hover:bg-paper-alt`,
  `hover:bg-paper-raised` (none of `paper-raised`, `paper-alt`, `rule-soft` were
  color tokens defined in `tailwind-next.config.js`). These were **real,
  pre-existing bugs** the check surfaced on its first run, initially left
  unfixed as out of this task's original scope — then fixed in a follow-up on
  this same branch once the design session confirmed the mappings and the
  scope was explicitly widened (§4.2). The test itself asserts nothing left in
  this set has quietly started compiling, so a stale allowlist entry can't
  silently outlive its reason — that assertion is what caught, mid-task, that
  all seven entries needed to come out once the fixes landed.
  `KNOWN_PREEXISTING_GAPS` is now an empty set, kept (not deleted) as the
  reviewed place a future genuinely-pre-existing gap would go.

`index.html`'s inline `<style>` block is treated as a second valid source of
"exists" deliberately, not as a workaround: its own opening comment says it holds
"the handful of things a utility class is the wrong tool for," kept above the
Tailwind `<link>` on purpose for source-order specificity. `tnum`,
`wl-freeze-1`/`wl-freeze-2`, `wl-cell`, `wl-cellbtn`, `wl-col`, `wl-chartchip`,
`wl-age-text` are real, intentional CSS classes styled there rather than via
Tailwind, and checking only `tailwind-next.css` for them would have made every one
a permanent, wrong "missing" finding.

## 4 · What today's run actually found (2026-09-28)

### 4.1 · First pass: both new tests failed, for one documented reason

**Both new tests initially FAILED against the committed `tailwind-next.css` — for
the same single reason, not two different ones.** Checked as the first diagnostic
step per the dispatch: a fresh rebuild of `tailwind-next.css` differed from the
committed file starting at byte 13,951 — the committed file was missing the rule
for `.px-\[8px\]`. `grep` confirmed `px-[8px]` was used in `app.js` (part of

i.e. the checks were not raising unrelated noise, they were correctly catching
the exact bug pattern this task exists to close, live, on the first night they
ran.

Per coordination with the "Resource Explorer expansion architecture" session,

affordance` and the By-analysis branch (`re/by-analysis-progressive-and-graph`,

branch wouldn't land a rebuild that goes stale again immediately.

### 4.2 · Second pass: scope widened, rebuilt, and the 7 gaps fixed

## 5 · CI wiring

`.github/workflows/resource-explorer.yml` had no Node/npm setup at all. Verified
(not assumed, per the peer session's prompt) that `node`/`npm`/`npx` themselves are
already present on `ubuntu-latest` — other tests here (`test_next_renders_text_
cross_check.py` and friends) already shell out to plain `node` with no setup step —
so no `actions/setup-node` was added. What *was* missing: `frontend-build/
node_modules` (gitignored, never installed in CI), which check 1's guard
(`shutil.which("npx")` + the `.bin/tailwindcss` existence check, §2) means both new
tests silently **skip** in CI without it — exactly the one place a stale CSS must
be caught, not the one place it silently isn't. Added one step, "Install
frontend-build JS dependencies" (`npm ci`, `working-directory: packages/
resource-explorer/frontend-build`), before the existing Postgres-schema step.
