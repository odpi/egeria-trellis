## How repo survey definitions are authored here

`docs/dr-egeria/repo_survey_types.csv` is the specification (one row per survey and step, ordered by `step_order`).
`scripts/generate_repo_survey_definition.py` turns it into the Dr.Egeria documents under
`docs/dr-egeria/survey-definitions/` and records each document's hash in `.generated.json`. The documents are
generated; they were regenerated by running the script, not edited. The same script derives the per-definition
"Link Element To Scope" question links from `question_catalog.yaml` through `REPO_ANALYSIS_SOURCE_STEPS`.
This is a repo-local workflow (a CSV plus a generator); the Dr.Egeria compact-spec/`refresh_specs` workflow of the
`dr-egeria-command-sync` skill is for commands and attributes and was not involved.

Dependencies, read from the step registry (`StepInfo`):

- All four declare `requires_context={"has_file_inventory": ...}`; the producer is `repo_file_inventory`, already
  step 2. Each needs `requires_resources={"zipball_root": "local_path"}` (a source view). None needs a clone
  (`git_clone_root`), a prior step other than the inventory, or to run last.
- The zipball is the one `repo_file_inventory` already downloads; `resolve_resources` acquires it once per
  `SurveyOrchestrator.run()`. So the four add no new fetch kind, no clone and no new credential. GitHub access
  is needed by the zipball, as it already was for step 2.
- The two reducers (`repo_foss_scorecard`, `repo_security_summary`) stay last. `repo_security_summary`'s
  `INPUT_KINDS` do not include the four, so there is no ordering constraint from it; they are placed before the
  reducers so a future widening of the summary's inputs does not need a reorder.

## Already-registered live definitions: the committed file and Egeria's copy now differ

The survey executor reads the definition from Egeria (`SurveyDefinitionReader.fetch`), not from the committed
document. Until the changed document is re-executed against Egeria, a run of "Assessment Survey" still runs the old
10 steps and the four are not run by it. Egeria's `RepoComplianceSurvey` and `RepoFullSurvey` are unaffected in
membership (Compliance's description text differs).

The drift is detected, not silent: `egeria_resync.py`'s `definition_drift` scan compares each live definition
against the committed documents (step list, order and descriptions) and will list `RepoAssessmentSurvey` as behind,
with the four as `missing`.

Republish path (a shared write; not performed here, needs the owner and a peer check):

1. Merge this branch.
2. Let the repair run: Admin -> Egeria Alignment -> `reauthor_survey_definitions`
   (`egeria_resync._do_reauthor_survey_definitions`), which calls `bootstrap.heal_batch` on the
   `survey-definitions` batch. It re-executes the documents in dependency order and then runs the declared
   post-heal script, `scripts/reconcile_survey_definition_links.py`. Do not hand-run the documents:
   `Link Next Process Step` is not idempotent and a duplicate edge makes the reader refuse the definition
   (`docs/egeria-operations.md` sections 2 and 9). The scope links come from `reconcile_survey_definition_scopes.py`.
3. Verify against the definitions, not the canary: `RepoAssessmentSurvey 14 steps`, `reconciler --dry-run` 0 duplicate
   / 0 stale (`docs/egeria-operations.md` 2.2), and `GET /api/egeria/resync/scan` no longer lists
   `definition_drift`.

Already-registered schedules naming `GovActionProcess::RepoAssessmentSurvey`
(`tests/test_schedule_survey_target.py` shows the shape) will start running the longer definition after step 2.

## Cost and runtime, from the code and the notes

- `repo_secret_scan`: `compute_cost="high"`, `fetch_cost="download"`; 277.3 s measured on `egeria_git`
  (`repo_survey_definition_adapter.py` comment), 330.8 s median over one run in `docs/funnel-cost-measured.md`.
  This is the dominant new cost: roughly five to six minutes on a large repository.
- `repo_telemetry_scan`: `medium` (VERIFY flag still in code); 24.1 s median, n=3.
- `repo_sla_content`: declared `low`; 20.2 s median, n=3. `repo_contribution_provenance`: declared `low`, no
  measurement found.
- Funnel numbers are per analysis, whole-run, from few samples; the secret-scan figure is n=1.
- Before: Assessment's cost was almost entirely `repo_git_statistics` and `repo_file_inventory`. Now one step
  roughly doubles to triples a large repo's Assessment wall time.
- Execution shape: `secret_scan` is `executes_at: prefect`, so the executor splits the chain into three
  dispatches: one batch (steps 1-7), the Prefect step alone, then one batch (steps 9-14). Each batch resolves the
  zipball itself; `GitHubClient.zipball_root` caches the ZIP by commit sha (`SourceCache`), so the second resolution
  costs an extraction (0.39 s measured) rather than a download. Prefect dispatch overhead is ~8-10 s per step
  (`Backlog.md`, measured 2026-09-18). This is the same shape Compliance and Full already have.
- Levers that already exist: `max_compute_cost='medium'` leaves out the secret scan, `max_fetch_cost='none'` runs
  nothing download-tier.

## When the four cannot run (pinned in `test_assessment_includes_compliance.py`)

- No GitHub access: the zipball is acquired before any step runs, outside any per-step try, so the orchestrator
  raises and writes no finding of the four kinds; the executor reports every step of that batch as status `error`
  with the cause (existing `test_run_batch_exception_is_caught_not_raised`). Consequence to know: a missing token
  fails the whole batch it is in, including the cheaper steps beside it; this was already true for `repo_file_inventory`.
- No inventory (and no producer in budget): each step is reported `skipped_by_design` with a reason; no finding
  with a pass-shaped label is written. Each step also states its own reason in its `requires_context`.
- No clone is involved, so a missing clone cannot affect these four.
