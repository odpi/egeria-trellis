## What this means for slice B step 2 and the zone step (facts only)
- The only Egeria-supplied route that creates a schema element and attaches it is a process whose inputs are text placeholders; it does not reference RE's database element. RE's own template create yields the same element for the same placeholders.
- A schema element created either way is its own anchor, outside the database element's anchored tree, so deleting the database element did not delete it (they were deleted separately).
- The cataloguer needs only the schema element's connection (embedded secrets-store connection and the file named by `secretsStorePathName`/`secretsCollectionName`); no relationship to a database element was needed.
- With no zone written, nothing refused any identity. The first rehearsal's lockout began only after RE wrote `ZoneMembership [egeria-runtime]`. No default zone exists to join on this build.
- The `catalogTargetName` of a process-created target is the schema's displayName (`<db>.<schema>`); a manually created one carries what the caller passes. `get_catalog_targets` returns each with `relatedBy.relationshipHeader.guid` and `relationshipProperties`.
- The process instance GUID returned by `initiate_gov_action_process` is not an engine action; engine actions are reached through its `ActionRequester` relationship and then `ControlFlow`.
- A survey with `includeSchemaNames=plain` produced annotations for that schema only (4), and RE's gateway `relationships` (above) would list the `ActionTarget` of a survey on the database element, as the first rehearsal also saw.
- Deletes by `erinoverview`, per element with SOFT_DELETE, `forLineage` true, cascade off, worked for every kind created, including engine actions and the process instance; deleting the database element removed its connection subgraph.
