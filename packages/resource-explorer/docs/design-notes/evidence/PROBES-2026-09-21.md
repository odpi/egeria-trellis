# Probe 9 investigation — coco_pharma SCRAM/no-password failure

Written up for the project owner's review, per a peer's ("Resource Explorer
expansion architecture") explicit request while probe 9 (native
annotation-type/metric-key dump) is on hold. Read-only investigation, no
Egeria or registry writes.

## 1. Connection shape on coco_pharma's freshly-catalogued asset

Traced the real relationship graph from the `RelationalDatabase` asset
(GUID `4dd8d5ee-eb5a-4fe3-8a52-7f304043a749`) via
`MetadataExpert.get_all_related_elements(guid, graph_query_depth=3)`
(`pyegeria`'s `ResourceConnection` / `EmbeddedConnection` relationships —
not a documented single-call API, had to walk the graph):

```
RelationalDatabase (coco_pharma)
  --ResourceConnection-->  VirtualConnection (GUID bf17d89f-2665-4f0e-ba84-cce4e3e0bc39)
      --EmbeddedConnection (label "basicAuthentication", position 0)-->
          Connection (GUID 1af83da6-5167-4823-a441-214392d40fe3)
          qualifiedName: "PostgreSQL Relational Database::host.docker.internal:5442::coco_pharma::SecretsStoreConnection"
          displayName:   "coco_pharma secrets store connection"
          configurationProperties: { "secretsCollectionName": "~{secretsCollectionName}~" }
```

**This is the root cause.** The embedded connection's own type is a plain
`Connection` entity (Egeria has no distinct `SecretsStoreConnection` entity
type here — it's identified by qualifiedName suffix and by being the
`basicAuthentication`-labeled embedded connection), and its only
`configurationProperties` entry, `secretsCollectionName`, holds the literal,
**unsubstituted Egeria template placeholder** `~{secretsCollectionName}~` —
not a real collection name. Whatever templating step is supposed to fill this
in during `deepCopy`-based cataloguing never ran, or ran against the wrong
template variable set. The connector has no collection to look up, so there
is no secret to resolve, which is exactly the shape of a Hikari
`SCRAM-based authentication... no password was provided` failure: not a
missing secret *value*, but a missing secret *reference*.

No `ConnectorType` relationship was reached for this embedded `Connection` at
depth 3 — it may need a deeper walk, but it's not needed to explain the
failure; the unresolved placeholder is sufficient on its own.

**This is a registration bug on RE's side, not a secrets-store design
problem** — found the exact skip. `EgeriaDatabaseSurveyor._catalog_and_survey`
(`resource_explorer/surveyors/database/egeria_database_surveyor.py`) builds
the `placeholderPropertyValues` dict passed to
`_create_postgres_element_from_template` (line 158) at two call sites — the
"PostgreSQL Server" element (lines 254–265) and the "PostgreSQL Relational
Database" element (lines 277–288). Both dicts set `databaseUserId` and
`databasePassword` (lines 262/264 and 285/287) but **never set
`secretsCollectionName`**. Egeria's template engine has nothing to bind that
placeholder to, so it's copied into the instantiated `Connection` element
literally, unsubstituted. This also explains why `_warn_if_database_has_no_
connection`'s check (line 185) passed for coco_pharma — it only checks that a
`Connection` exists at all, not that its secrets reference resolves, so
"has a connection" and "survey will actually authenticate" came apart here.

## 2. Where the quickstart resolves secrets for its own bundled surveys

Confirmed by inspecting (structure only, not contents) the engine host
container's filesystem:

```
quickstart-egeria-main:/deployments/secrets/
  egeria-servers.omsecrets
  integration.omsecrets
  coco-user-directory.omsecrets
```

plus `/deployments/lib/yaml-secrets-store-connector-6.2-SNAPSHOT.jar` — a
file-based (YAML) secrets store connector, as the peer's hypothesis said,
mounted into the engine host container. This matches "ISSUE-79"'s earlier
write-up of this folder as a cataloged `FileFolder`. None of the three
existing `.omsecrets` files are named for a Postgres survey collection
(`egeria-servers`, `integration`, `coco-user-directory` — none match
`secretsCollectionName` conventions for a database connection), which is
consistent with item 1: even if the placeholder *had* been substituted, there
is no evidence a matching collection exists yet for `coco_pharma`'s survey
credentials. Did not open file contents — this was a structural check only.

**So a working native survey needs two fixes, not one, and they're
independent:**

1. **Bind the placeholder** — pass a `secretsCollectionName` in the
   `placeholderPropertyValues` dict at the two call sites in item 1, so the
   instantiated `Connection` actually references a real collection name
   instead of the literal template string.
2. **The referenced collection has to exist** — a `.omsecrets` file (or an
   entry in an existing one) in `/deployments/secrets/` matching whatever
   name step 1 supplies, containing the real `coco_pharma` credentials.
   Nothing observed here confirms that collection exists yet — the three
   present today are for other purposes.

Fixing only (1) with a collection name that doesn't exist in (2) trades one
failure signature for another (unresolvable reference vs. unbound
placeholder) — both still surface as "no password provided," not a working
survey.

## Fixed (2026-09-21, same day)

**Decision (project owner, 2026-09-21):** Egeria does not share secrets
across clients — RE keeps its own secrets store, using Egeria's own
client-side-secret structure (https://egeria-project.org/concepts/client-side-secret),
rather than pointing at Egeria's bundled `*.omsecrets` files (item 2 above —
those hold Egeria's own bootstrap credentials for unrelated purposes, and
none are named for a database RE surveys).

`EgeriaDatabaseSurveyor` (`egeria_database_surveyor.py`) now:

1. Finds-or-creates one RE-owned `Connection`/`Endpoint`/`ConnectorType`
   graph using the YAML File Secrets Store Connector's provider class
   (`_ensure_own_secrets_store_guid`), pointed at RE's own file
   (`EgeriaConfig.secrets_store_path_name`, now defaulting to
   `/deployments/secrets/resource-explorer.omsecrets` — the same bind-mounted
   directory every deployment profile already gives the engine host
   container, so no new mount is needed).
2. Writes each database's credentials into that store as a collection named
   for its slug (`_save_database_secret`, via `AutomatedCuration.
   save_client_side_secret` — a call this codebase had configured for
   (`EGERIA_SECRETS_STORE_GUID`/`EGERIA_SECRETS_STORE_PATH_NAME`, confirmed
   live 2026-07-09) but never actually wired to a caller).
3. Passes both `secretsCollectionName` and `secretsStorePathName` as
   `placeholderPropertyValues` on the two `_create_postgres_element_from_
   template` calls in `_catalog_and_survey` — but only when at least one of
   the server/database elements is actually being freshly created, since a
   pure reuse-by-qualifiedName run never re-runs `deepCopy` and a secrets
   write for it would be wasted (see `CATALOG-AND-SURVEY-REFRESH-FIX.md`).

Unit-tested in `tests/test_egeria_database_surveyor_secrets.py` (collection
naming, request body shape, find-or-create, non-fatal failure handling).
**Not yet live-verified** — this fixes only *fresh* catalog runs, so proving
it end-to-end needs a database slug that has never been cataloged before
(neither `coco_ods` nor `coco_pharma` qualify — both already exist by
qualifiedName in Egeria, so re-running `_catalog_and_survey` against either
would hit the reuse path and never exercise this code at all). See
`CATALOG-AND-SURVEY-REFRESH-FIX.md`'s follow-up #4 for the full note on how
this relates to that doc's earlier "hand-assembling the database's own
connection subgraph is an unsupported workaround" ruling — this is a
different, generic, supported use of `ConnectionMaker`, not a revisit of that
ruling.

**`coco_ods` and `coco_pharma` are not fixed by this and must not be treated
as such.** Both already exist in Egeria by qualifiedName, so every future
`_catalog_and_survey` call against either hits the reuse path and never
re-runs `deepCopy` or writes a secret — their existing `SecretsStoreConnection`
stays bound to the literal `~{secretsCollectionName}~`/`~{secretsStorePathName}~`
placeholders exactly as found in items 1 and 3 above, unchanged by this fix.
Making either work needs the delete-and-recatalog GAP process
(`config/technology_type_processes.yaml`) run against it first, which is the
same real, deliberately-deferred decision `CATALOG-AND-SURVEY-REFRESH-FIX.md`'s
finding #4 already flagged (GUID change, orphans existing Survey
Reports/annotations) — not something this change reopens or resolves. Probe 9
cannot pass against either asset until that decision is made and acted on.

**Reachability — quickstart-specific, confirmed structurally, not assumed.**
`save_client_side_secret` is an Egeria API call (`AutomatedCuration`, routed
through the view service), not a direct file write from RE's host process —
RE never touches `/deployments/secrets/resource-explorer.omsecrets` itself.
Confirmed live (`docker exec quickstart-egeria-main`) that `qs-view-server`,
`qs-engine-host`, `qs-metadata-store` etc. are all names for OMAG servers
hosted inside the *same single* `quickstart-egeria-main` container/platform
process — one filesystem, so a write the view service makes is immediately
visible to whatever the engine host reads at native-survey time, no separate
mount required. This has only been confirmed for the quickstart topology RE
actually targets (`docker-compose.yaml`'s `EGERIA_VIEW_SERVER: qs-view-server`
throughout `optional-associated-runtimes/trellis`) — a genuinely multi-host
deployment, where the view service and engine host are different containers
on different filesystems, was not checked and may need its own mount.

**Collection naming and slug renames.** `_secrets_collection_name(db_slug)` is
a pure function of the slug passed in at call time — nothing persists a
naming decision separately from the registry, so it can't go stale on its
own. A slug rename (`registry.rename_project_slug`) doesn't change the
Egeria-side `qualifiedName` (server/database name, not the RE slug) an
already-cataloged element reuses, so a rename never triggers a fresh
`_create_postgres_element_from_template` call and never needs a new secret —
the collection written under the pre-rename slug stays the one the existing
Connection already references and keeps working. Only a genuinely new
database registration computes and writes a collection name, always from
that registration's current slug.

**This derive-on-every-call approach breaks the moment a reachability check
exists, and must not be carried forward as-is.** Flagged by a peer review: a
future "does the collection I bound actually exist?" check would re-derive
the name from the *current* slug and compare it against what the engine host
still reads from the *registration-time* slug — after a rename these two
diverge, and the check would report "missing" for a collection that is
present and working under its old name. The derive-every-time approach in
this PR is safe today only because nothing yet reads the name back for
comparison; it stops being safe the moment something does. **Before building
that check:** persist the bound collection name on the registry row at
catalogue time (e.g. a `databases.secrets_collection_name` column) and have
both the check and any later re-write read that column back rather than
re-deriving it. Filed here rather than fixed now — no reachability check
exists yet for this to matter to.

## Live end-to-end verification: SUCCEEDED (2026-09-21) — and it found three more real bugs

Registered `egeria-optional-prefect-server`'s own backing Postgres database
(`egeria-shared-postgres:5442/prefect`, 36 tables — the Prefect server
container's own database, chosen specifically because it has never been
catalogued by RE and needed no new infrastructure) as a genuinely
never-before-catalogued RE database (slug `egeria_optional_prefect_db`), then
called `EgeriaDatabaseSurveyor.catalog_and_survey(...)` directly. The fresh
`deepCopy` path plus the fix above bound both placeholders correctly on the
first structural check — but the live run surfaced **three further bugs in
`_ensure_own_secrets_store_guid`**, all found and fixed in the same session,
each confirmed by tracing Egeria's own server-side Java source (a local
checkout matching the running platform's version):

1. **`save_client_side_secret` needs an Asset guid, not the bare Connection's.**
   `AutomatedCurationRESTServices.saveClientSideSecret` calls
   `ConnectedAssetClient.getConnectorForAsset(userId, secretsStoreGUID, ...)`
   — passing the Connection's own guid fails with `OMAG-REPOSITORY-HANDLER-
   404-001 ... retrieved an object ... of type Connection rather than type
   Asset`. Fixed: `_ensure_own_secrets_store_guid` now also creates a generic
   `Asset` (`AssetProperties`) and links it to the Connection via
   `ConnectionMaker.link_asset_to_connection`, returning the **Asset's** guid.
2. **`ConnectionMaker`'s `link_connection_connector_type`/`link_connection_
   endpoint`/`link_asset_to_connection` all default `body=None`, and that
   default silently creates no relationship at all** — no exception, no
   error, just nothing. First surfaced as `save_client_side_secret` failing
   with `Null connectorType property passed in connection`, days after the
   link calls that should have attached one had already "succeeded". Fixed:
   every link call now passes an explicit `{"class":
   "NewRelationshipRequestBody"}`.
3. **`YAMLSecretsStoreProvider` (what Egeria's own docs and the Postgres
   content-pack templates use) instantiates the read-only base class
   `YAMLSecretsStoreConnector`, not `YAMLSecretsFileConnector`.**
   `AutomatedCurationRESTServices.saveClientSideSecret`'s own code only calls
   `saveSecretsCollection()` when `connector instanceof
   YAMLSecretsFileConnector` — with the wrong provider that check silently
   fails and the endpoint returns a plain success `VoidResponse` having done
   nothing. `YAMLSecretsFileProvider` is the sibling provider class that
   actually instantiates `YAMLSecretsFileConnector`. **This distinction only
   applies to a secrets-store Connection something WRITES through** — the
   per-database `SecretsStoreConnection` embedded via `deepCopy` (read-only,
   consumed at native-survey time) correctly keeps
   `YAMLSecretsStoreProvider`, matching Egeria's own documented pattern.
4. **The admin Connection itself needs a placeholder, non-null
   `secretsCollectionName` configuration property**, or the OCF secrets-store
   connector framework's own `start()` refuses to initialize at all
   (`OCF-CONNECTOR-400-009 ... secretsCollectionName was not supplied`), even
   though `YAMLSecretsFileConnector.start()` immediately nulls it back out
   and every real save call supplies its own collection name as a method
   argument. Fixed with a fixed placeholder value
   (`"resource-explorer-admin"`) that is never actually read.

Two of these four (#2, #3) are real upstream gaps, not RE-side workarounds
to carry forward quietly — logged in `egeria-python`'s `PYEGERIA_ISSUES.md`
(2026-09-21) rather than fixed in place, per that repo's standing
pyegeria-gaps-tracking convention: **ISSUE-111** (pyegeria — `ConnectionMaker`'s
silent no-op on `body=None`) and **ISSUE-112** (Egeria server —
`saveClientSideSecret` returning success on the wrong connector class), each
with the file:line this write-up traced. #1 and #4 are calling-convention
requirements of the real, correctly-implemented API (an Asset is genuinely
what the endpoint needs; a connector genuinely can't start with no collection
name configured) — surprising, not defective. Once all four were addressed,
a clean re-run (after deleting the partially-built
SecretsStore graph and the two half-cataloged database/server elements —
routine cleanup for a test asset, not the `coco_ods`/`coco_pharma`
delete-and-recatalog decision, which stays open) produced:

- `_save_database_secret` returned successfully, no warning.
- The templated `Connection`'s `secretsCollectionName` bound to
  `"egeria_optional_prefect_db::PostgreSQL Secret"` (confirmed live, not the
  literal placeholder) and its `secretsStorePathName`/`networkAddress` bound
  to `/deployments/secrets/resource-explorer.omsecrets` (confirmed live).
- The triggered native `survey-postgres-database` engine action reached
  **`final_status: COMPLETED`** (not `FAILED`) in ~225 seconds:
  `OMES-SURVEY-ACTION-0019 ... completed the analysis of asset
  45a75724-dbd3-45c6-bcd3-203db34265db ... survey report
  46636792-8f55-4fef-91b6-38f9870092e0`.
- The survey report holds **222 real `ResourceMeasureAnnotation`s** across 4
  annotation types (`Capture Database Measurements` ×1, `Capture Database
  Schema Measurements` ×1, `Capture Database Table Measurements` ×38,
  `Capture Database Column Measurements` ×182), all under analysis step
  "Profiling Associated Resources", with `resource_properties` spanning
  database/schema/table/column-level measures (row counts, sizes, column
  types, distinct-value counts, index/trigger/rule flags, and more — 37
  distinct property names total across the four types).

This closes the loop the "two fixes, not one" section above opened: both the
placeholder binding and a real, existing secrets collection were required,
and now both are true for a fresh catalog run.

**"Frequent Values for Column" — native, present, not a distinct annotation
type.** Peer review question: the design's §1.4 lists this (from the
annotation-type enum, not a prior run) as something the Postgres survey
produces, and this report shows only 4 `ResourceMeasureAnnotation` types,
no `ResourceProfileAnnotation`. Traced the actual Java
(`PostgresDatabaseStatsExtractor.java`, `postgres-server-connectors`):
`postgres-database-survey-service` never constructs a
`ResourceProfileAnnotation` anywhere — every annotation it builds is a
`ResourceMeasureAnnotationProperties` (database/schema/table/column level,
confirmed by grepping every `new ResourceMeasureAnnotationProperties()`
call site, 4 total, matching this run's 4 types exactly). "Frequent
values" is real, but it's **not** a separate annotation — it's two
`resourceProperties` keys on the *column-level* `ResourceMeasureAnnotation`
itself: `Most Common Values`/`Most Common Values Frequency`
(`RelationalColumnMetric.MOST_COMMON_VALUES`/`_FREQUENCY`), sourced
directly from Postgres's own `pg_stats.most_common_vals`/`most_common_freqs`
system-catalog columns. **Confirmed present with real content in this run**
— several column annotations in the captured dump carry genuine
`Most Common Values` arrays (e.g. real `prefect.resource.id`/
`prefect.resource.name` JSON values from the `event_resources` table).
**No request parameter or analysis step gates this** — the code path that
reads `most_common_vals`/`most_common_freqs` runs unconditionally for
every column row `pg_columnStatsSQLCommand` returns; the only real
precondition is Postgres-side, not Egeria-side: `pg_stats` only has a row
for a column once Postgres's own `ANALYZE` has run against that table
(routine autovacuum/autoanalyze behavior, not something this survey
service triggers or checks for). **For RE's own column-profile step**:
frequent values are native to the existing `ResourceMeasureAnnotation`
column data already being read — no separate rule-C computation needed to
get this specific fact, only to decide what to do with a column Postgres
has never analyzed (empty/null `most_common_vals`).

**Endpoint host — confirmed `host.docker.internal:5442`, single-container
only.** The bound `Connection`'s JDBC endpoint (and the registered
`DatabaseEntity.egeria_host`) used `host.docker.internal:5442` throughout
this run, and it worked — but only because quickstart's `qs-view-server`/
`qs-engine-host`/`qs-metadata-store` all run inside the *same* single
`quickstart-egeria-main` container (already established in item 2 above):
the engine host reaches the target Postgres by bouncing out to the Docker
host and back in via the published port, same as reaching `localhost:5442`
would from the host itself. **This is not general** — a genuinely
multi-host or multi-container deployment (the target Postgres and the
engine host on different containers, no single Docker Desktop host to
bounce through) would need the container-network-reachable name (e.g.
`egeria-shared-postgres:5442`, the name the Prefect server's own
`PREFECT_API_DATABASE_CONNECTION_URL` already uses internally) instead of
`host.docker.internal`, or the connection genuinely fails to reach the
resource at all — the `network_unreachable` case rule B still has to
handle, distinct from both `OPEN-SURVEY-0009` (no connection) and the
SCRAM/no-password case this write-up otherwise covers.

**One thing not independently re-verified**: whether `.omsecrets` file
creation is genuinely automatic on a truly first-ever write. An empty
`resource-explorer.omsecrets` (`secretsCollections: {}`) was created by hand
before the final successful run, once it became clear the earlier failures
were connector-class issues, not a missing-file issue — Egeria's own
`YAMLSecretsFileConnector.saveSecretsCollection` source does call
`secretsStoreFile.createNewFile()` when the file is absent, so auto-creation
should work once the correct connector class is in use, but this was not
re-tested from a state with no file present at all.

## Probe 9 done properly, against fresh `coco_ods`/`coco_pharma` (2026-09-21, post-redeploy)

The project owner's full Egeria wipe-and-redeploy that same evening cleaned
up both `coco_ods` and `coco_pharma`'s broken pre-existing elements as a side
effect — the delete-and-recatalog decision above became moot rather than
needing its own ruling. This let Phase 1 slice #6 (COORDINATOR-BRIEF-
MULTI-RESOURCE.md) — "re-catalogue `coco_ods` with a reachable connection;
run native `survey-postgres-database`; dump every annotation type and metric
key" — actually run, for the first time this session against real Coco
Pharmaceuticals data rather than the Prefect-Postgres stand-in above.

**It did not work on the first try.** Re-cataloguing against the fresh
platform surfaced three more real bugs in the exact machinery this write-up
already covers, each hiding behind the previous one:

**Bug 5 — `_ensure_own_secrets_store_guid` only checked the final Asset for
existence, not each sub-element.** After the wipe, this method's own
`ConnectorType` was found to already exist (origin unconfirmed — plausibly a
partial leftover from an interrupted attempt) while the `Endpoint`/
`Connection`/`Asset` did not. Gating all creation on the Asset alone made the
very first `create_connector_type` call blow up with a 409 duplicate-
qualifiedName instead of finding and reusing what was there. **Fixed**:
find-or-create each of the four sub-elements individually
(`egeria_database_surveyor.py`).

**Bug 6 — the link calls were gated on "just created," not run
unconditionally.** Once bug 5's fix let the method *find* an existing but
unlinked `Connection` rather than creating a fresh one, it skipped
`link_connection_connector_type`/`link_connection_endpoint` entirely,
because those calls sat inside the `if not connection_guid:` branch. The
found Connection was a partial leftover — present, but never actually linked
to its `ConnectorType`/`Endpoint` — the exact "reuse never repairs" defect
this whole method exists to avoid, one level up. Egeria surfaced this
immediately and correctly: `OCF-CONNECTION-400-003 Null connectorType
property passed in connection`. **Fixed**: both link calls now run every
time, live-confirmed as a safe no-op-on-repeat rather than a duplicate or
error.

**Bug 7 — `ConnectionMaker.create_connection`'s direct (non-template) body
silently drops `configurationProperties`.** Live-confirmed on two separate
Connections this session: the admin secrets-store's own `Connection` (needs
a placeholder `secretsCollectionName` to satisfy the OCF framework's
`start()` precondition — bug from the original write-up above) and the
per-database `SecretsStoreConnection` embedded by the PostgreSQL template
(needs `secretsStorePathName` alongside `secretsCollectionName`) both came
back from the server with `configurationProperties` entirely absent, despite
both being supplied in the creation call's body. This is different from
bug 3/4 above (wrong connector *class*) and from the missing-placeholder
precondition (fixed by supplying a value) — this is the value being supplied
and not landing at all. Confirmed by patching both directly with
`update_connection(..., mergeUpdate=True)` afterward, which *did* take
effect immediately. **Not yet fixed at the source** — patched live only, for
both `coco_ods` and `coco_pharma`'s admin-store Connection and their
per-database `SecretsStoreConnection`s. Filed as a gap (see `docs/Backlog.md`)
rather than guessed at, since it needs someone to check whether this is a
`ConnectionMaker.create_connection` client-side body-shape bug (candidate for
`PYEGERIA_ISSUES.md`) or an Egeria server-side handling difference between a
template-instantiation body and a direct-creation body for this property —
the *template* path (`_create_postgres_element_from_template`'s own
`placeholderPropertyValues`) has never shown this symptom.

**Bug 8, found but not investigated — the leftover `ConnectorType` from bug
5 carried the wrong connector class** (`YAMLSecretsStoreProvider`, the
read-only one — bug 4 from the original write-up, above). Reusing it by
qualifiedName silently carried the old defect forward even though the
*code* creating a fresh one had already been fixed — a third instance of
"reuse never repairs," this time of a bug that was already fixed for new
creation. Patched live via `update_connector_type`. Not yet decided whether
the source should *verify* a found ConnectorType's `connectorProviderClassName`
before trusting it, or whether this specific stale element was simply a
pre-fix leftover that a clean platform will not reproduce going forward —
logged to `docs/Backlog.md` for a decision rather than guessed at.

## Probes 4 and 5, run live (2026-09-21) — unblocking Phase 1 slice #10's gate

Both from `egeria-support-for-multi-resource.md` §9, run against the fresh
platform to settle §3's open DRAFT-status question and §10's filing table
left pending. Scratch elements cleaned up afterward, verified by an
independent re-read (annotation count on the real `coco_pharma` survey
report returned to its exact 91-row baseline post-cleanup).

**First pass at probe 4 tested the wrong field entirely — corrected below.**
The initial run tested `create_data_class`'s `initialStatus: DRAFT`, which
sets `ElementStatus` — Egeria's generic entity persistence/lifecycle status
(`ACTIVE`, `DELETED`, ...), not what design §3's actual decision was about.
Re-reading §3 (and the Java source it cites) caught this: the mechanism §3
proposed is `contentStatus`, a *domain property* on
`AuthoredReferenceableProperties` (`ContentStatus.java`,
`AuthoredReferenceableProperties.java:58-59`, confirmed live in the local
Egeria checkout) — a completely different field, describing whether the
*content* is complete, not whether the *entity* exists/persists.
`AnnotationProperties`, `DataClassProperties`
(`DataValueSpecificationProperties`), and `ValidValueDefinitionProperties`
all extend it, per the class's own `@JsonSubTypes` list — so both of §3's
proposed carriers (a proposal annotation, or the candidate governance
element itself) can carry it.

**Probe 4, corrected — `contentStatus: DRAFT` inside `properties`: WORKS
CLEANLY, for both carriers.**

Tested both, each as its own scratch element, cleaned up after:

- `DataDesigner.create_data_class({"properties": {"contentStatus": "DRAFT",
  ...}})` — created, read back by guid: `contentStatus` round-trips as
  `DRAFT`. The element's separate, overall lifecycle status stays `ACTIVE`
  throughout — fully persisted and normally visible, just flagged as
  content-incomplete via the domain property. The two statuses are
  independent, exactly as the Java source's own field separation implies.
- `DataDiscovery.create_annotation({"properties": {"contentStatus": "DRAFT",
  ...}})` (a `DataClassAnnotation`, attached to the real `coco_pharma`
  survey report from probe 9) — same result: `contentStatus` round-trips as
  `DRAFT`, lifecycle status stays `ACTIVE`.

(The original, mistaken test of `initialStatus`/`ElementStatus` is still
worth recording, since it surfaced two real, separate findings along the
way: `NewElementRequestBody` genuinely has no `initial_status` field and
silently drops it client-side — logged as ISSUE-113 in pyegeria's
`PYEGERIA_ISSUES.md`, PR opened against upstream `odpi/egeria-python` — and
a raw REST call bypassing pyegeria confirmed the *server* also does not
honor `initialStatus` for this particular creation endpoint. Both remain
true and worth fixing/investigating on their own terms; neither is the
mechanism §3 actually needed, so neither blocks the DRAFT-content-proposal
path this section is about.)

**Decides §3's open question, in the positive**: proposing a new governance
element, or a proposal-carrying annotation, as genuinely incomplete/
unconfirmed content — the mechanism §3's project-owner decision hoped might
replace the "candidate-carrying annotation subtype" ask — **works today**,
via `contentStatus`, no pyegeria fix or Egeria change needed. This does drop
the §3 "type ask" tier: no new `candidateDataClassSpecification`/
`ReferenceDataAnnotation`/`DataScopeAnnotation` fields are needed — a
proposal is a normal `DataClassAnnotation`/`DataGrainAnnotation`/etc. (or,
for the element-creation path, a normal `DataClass`/`ValidValueDefinition`)
with `contentStatus: DRAFT` set, linked to its originating evidence via
`AssociatedAnnotation` per §3's own earlier reading.

**The open visibility question sharpens, rather than resolves, given this
correction.** The earlier concern (`QueryOptions.limitResultsByStatus`
defaulting to `null`/"all statuses") was about `ElementStatus`, and is now
confirmed *not* the live risk here — a `contentStatus: DRAFT` element's
`ElementStatus` stays `ACTIVE`, so it was never going to be excluded by an
`ElementStatus` filter regardless. The real, still-open question is
different and arguably sharper: **does a normal read/render path check
`contentStatus` at all**, or does an ordinary consumer see a
`contentStatus: DRAFT` annotation/DataClass rendered exactly like a
confirmed one, with no visual or programmatic distinction? Not checked
here — this needs its own probe (does RE's own annotation rendering, or a
naive `find_metadata_elements` consumer, surface `contentStatus`
anywhere?) before relying on `contentStatus: DRAFT` as a safe default for
unconfirmed proposals.

## Probes 7 and 8, run live (2026-09-22) — unblocking Phase 1 slice #13's gate

Egeria-support-for-multi-resource.md §5 filed `resource_reachability` as
**deferred (2026-09-21)** — "do not build it yet ... further tests" — pending
exactly this live run. **The project owner reversed that deferral on
2026-09-22 and asked for slice #13 (the reachability probe, the
`resource_reachability` table, the classic-UI launcher sentence) to proceed
now.** See `RESOURCE-REACHABILITY-IMPLEMENTED.md` for the
built feature; this section is the live evidence it's built from.

Peer-checked before the live write (this session's standing discipline):
`mcp__ccd_session_mgmt__list_sessions` showed no other session `isRunning`
at the time; a heads-up was sent anyway to the live "Resource Explorer
expansion architecture" session before triggering anything, per this
session's own coordinate-before-shared-writes practice — no objection, and
a useful peer review came back on the outcome vocabulary and a
derive-vs-persist trap (both incorporated into the built feature — see the
design notes doc).

**First pass — no Connection on the folder Asset at all: `no_connection`,
not `reachable`, and this is the RE-relevant default, not an edge case.**
Created a scratch DataFolder Asset the same way
`EgeriaFileSystemSurveyor.catalog_and_survey` does for every real filesystem
RE has ever cataloged (`AutomatedCuration.create_folder_element_from_
template`), then ran the probe exactly as the design doc specifies:

```python
AutomatedCuration.initiate_gov_action_type(
    action_type_qualified_name="FileSurvey::survey-folder",
    action_targets=[{"actionTargetName": "sourceFile", "actionTargetGUID": folder_guid}],
    request_parameters={"finalAnalysisStep": "CHECK_ASSET"},
)
```

Result: terminal status `INVALID` in ~6s, completion message:

```
OPEN-SURVEY-0009 The folder-survey-service Survey Acton Service has been
supplied with asset 2175e567-92a7-4b5b-9eac-bc2f41910aa2 which has no
connection, so there is no way to reach the resource it describes
```

**This is a real, previously-unconfirmed finding, not a probe mistake.**
`egeria_filesystem_surveyor.py`'s own existing comment already suspected
this ("the DataFolder/DataFile templates it uses have no attached Connection
subgraph the way the PostgreSQL templates do") but flagged it as an
*unverified* concern specific to the native FileDirectory survey. This run
confirms it directly, and confirms the consequence: **every filesystem RE
has ever cataloged this way will report `no_connection` from a reachability
check, not a genuine reachability answer**, until something attaches a real
Connection to the folder Asset — which nothing in RE's filesystem cataloging
path does today. Scoped out of this slice's build (see the design notes doc)
rather than silently assumed away.

`analysisLevel=ALL_FOLDERS_AND_FILES` (probe 8) against the same
no-Connection asset produced the identical `OPEN-SURVEY-0009` result —
expected, since there is no connection to survey at any recursion depth.

**Second pass — a Connection attached, pointed at a path the engine host's
own filesystem cannot see: `network_unreachable`, not `no_connection`, and
still fast.** Built a real Connection/Endpoint/ConnectorType graph
(`ConnectionMaker`, `BasicFolderProvider` — the same three-element,
find-or-create, always-relink pattern `egeria_database_surveyor.py`'s
`_ensure_own_secrets_store_guid` already established for the admin
secrets-store Connection, including the explicit
`{"class": "NewRelationshipRequestBody"}` body on every link call), pointed
at `/tmp/re_reachability_probe7b` — a macOS host path, since the engine host
(`quickstart-egeria-main`) runs in a Docker container and cannot see the
host's `/tmp`. Result: terminal status `FAILED` in ~3s:

```
OMES-SURVEY-ACTION-0018 The survey action service folder-survey-service
threw a org.odpi.openmetadata.adapters.connectors.datastore.basicfile.ffdc.
exception.FileException exception ... BASIC-FILE-CONNECTOR-404-001 The
folder named /tmp/re_reachability_probe7b in the Connection object
ResourceExplorer::Probe7bReachabilityScratch::Connection does not exist
```

This is the folder-survey analogue of the "genuinely multi-host deployment"
caveat probe 9's write-up already flagged for the database case
(`host.docker.internal`, "a genuinely multi-host or multi-container
deployment ... would need the container-network-reachable name ... or the
connection genuinely fails to reach the resource at all") — confirmed here
for filesystems specifically, not assumed to generalize from the database
case.

**Third pass — a Connection attached, pointed at a path the engine host CAN
see: `reachable`, `COMPLETED`, fast.** Same graph, `networkAddress` pointed
at `/deployments/coco-data-lake` — confirmed present via `docker exec
quickstart-egeria-main ls /deployments/coco-data-lake` before the run, a
path genuinely inside the engine host's own container filesystem. Result:

```
OMES-SURVEY-ACTION-0019 The survey action service folder-survey-service has
completed the analysis of asset e0eb9167-cc01-4360-9870-6121d3421cca with
request type survey-folder in 3407 milliseconds; the results are stored in
survey report bc2fdec2-11dd-4f85-b409-1bbd408f0030
```

`analysisLevel=ALL_FOLDERS_AND_FILES` against the same reachable asset also
completed (`COMPLETED`, 3378ms) — the folder was empty

**Confirms the design doc's core premise**: all three outcomes completed in
