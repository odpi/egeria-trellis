Same hatching, different sentence, and only one of the two carries an action. That is the distinction EngineCapabilities was added to preserve, in its own words: declaring a capability true ahead of the code that reads it would make “not yet implemented” render identically to “measured, and there was nothing”.

Three · not a design question — a rendering rule the shipped column needs

distinct_count is REAL, correctly, because Postgres' n_distinct is negative when it expresses a ratio rather than a count: above zero it is an estimated number of distinct values; below zero it is the negative of that number divided by the row count. So −0.8 means distinct values are about 80% of rows.

A card that prints the field as a count renders “distinct: −0.8” — a negative cardinality, which cannot happen. It is the same shape as the counter-reset case from round 1: a real number, rendered as the wrong kind of quantity, and read as an error in the data rather than in the view.

wrong
distinct −0.8
right
−0.8 → ~80% of rows
1274 → 1,274 values

One branch on the sign, at the render site. Worth a test, since the sample data in coco_pharma may well contain only one of the two forms, and the bug would then ship invisible.

Still to draw, and why not here

The treemap and the exposure heatmap. The card is drawn first because it is the one with a committed schema behind it, so it is the one where a drawing can be wrong in a way that costs a migration. The treemap needs the inventory rows to be checked the same way — area and colour must come from fields that exist, and the hatched “could not read” region needs whichever state the FS walk records for an unreadable directory. The heatmap needs the role side, which is slice 8/9 (postgres_operations) and not yet there: drawing a columns-by-roles grid before the roles exist would be designing against a guess, which is the thing round 2 was created to stop.
