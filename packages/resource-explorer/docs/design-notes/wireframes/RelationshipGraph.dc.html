Relationship Graph · drawn from the real edges, not a mock

AdventureWorks’ 91 foreign keys, at three zoom levels

Every edge here was fetched on 28 Sep from GET /api/databases/laz_local_adventureworks/survey-results, the db_relationship_graph result the By-analysis tab is built from, and laid out with Graphviz (dot). Nothing is illustrative. The counts match the analysis exactly: 68 tables, 91 keys, 20 of them crossing a schema boundary, 2 components, 1 table with no keys at all. Arrows point at the table being referenced, so many arrows into a node make it a hub.

One · the schema map, the entry point at any size

Five nodes and ten lines, whatever size the database is. It answers the owner’s question at a glance: sales leans on person (8 keys), purchasing on production (3), and everything eventually reaches humanresources.employee. Not drawn: hr, pe, pr, pu, sa, which hold only views (views declare no keys), and public, which has no tables. The caption has to say so, or six of the eleven schemas silently vanish.

Two · the whole database, 68 tables: at this size it still reads

It works at 68 tables because of three choices, and each one matters: schemas as boxes; hubs in weight, with their in-count (product ←14, person ←7, employee ←6); and cross-schema keys darker than keys inside a schema. A force layout (fdp) of the same data was noticeably worse, so clustering does the work here, not the algorithm. Somewhere around 100 tables this stops reading, and the drawing should fall back to the map plus the hub list the analysis already ranks. transactionhistoryarchive is the one table with no keys in or out. It's drawn solid and labelled, because it was measured. Dashed is reserved for keys that point outside what was captured (none here).

Three · one schema opened: why the edges leaving it have to be drawn

A finding the drawing turned up. The analysis's own per-schema result says sales has 3 components and 2 isolated tables, salestaxrate and shoppingcartitem. Neither is isolated: one references person.stateprovince, the other production.product. Across the whole database, sales is entirely inside the main component. The "3 components" is an artefact of cutting the graph at the schema boundary. The rollup text says cross-schema keys "are counted in NO schema's own edge count", which is right as bookkeeping, but it means the per-schema words isolated and components describe the cut, not the tables.

So two rules. A per-schema drawing always draws the keys that leave it, as lines to the named tables outside, as here. A per-schema sentence says "no keys inside sales", never "isolated". Isolated is a claim about the database, and only the database-level result can make it. This also changes what the Questions and By-analysis rollups say for sales today.

Four · getting it into /next

The pipeline exists: factMermaid() → Kroki → a pane, already used for repos. Two adjustments. Emit Graphviz, not Mermaid: Kroki renders both, and Mermaid's layout has nothing comparable to dot's clusters, which the whole-database view depends on. That means a sibling to /api/diagrams/mermaid and a graphviz field beside mermaid on the fact. Emit three sources, not one: the map, the whole graph when it is under the size limit, and one per schema with its outgoing keys. The pane opens on the map.

Static first. The version worth having later lets you click a table and land on it in the Schema Inventory tree. That needs a graph library in the browser, which /next doesn't have. Worth choosing on purpose, not drifting into. Keys are read from the catalog, so a limited credential like coco_pharma's should still get the complete graph. That makes this one of the few whole pictures that database gets.
